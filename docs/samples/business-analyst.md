# Lumen Business Analyst onboarding

This is a fictional Lumen exercise, not the FirstDay repository or instructions for a real employer. Use invented examples and keep notes as unsent practice artifacts. No real interviews, approvals, purchases or operational changes are part of this exercise.

## Before you start: brief and vocabulary

Read this guide and the fictional product brief LUM-101: Improve the welcome checklist. The exercise outcome is to help a new joiner understand a task before deciding to mark it complete. Its scope is choosing a role, reading a task, inspecting its published guide and marking the task complete; automated completion and manager approval are outside the exercise scope.

Use these glossary definitions consistently. A Learner is a person using onboarding knowledge while joining an organization or taking on a role. A Checklist task is an onboarding action a learner can mark complete or incomplete themselves. A Published guide is a maintained knowledge document whose active version is fully indexed and available to learners. A Job role is an onboarding audience, not an access permission.

## Discovery notes

Separate discovery notes into Observation, Assumption and Question. An Observation records what the fictional scenario explicitly shows: Demo Joiner A opens a task before deciding whether to complete it. An Assumption is unverified: opening a guide might help the learner understand the task. A Question records a gap: what explanation would make the completion choice clearer? Do not present assumptions as findings or invent interviews with real people.

## Requirement template and acceptance criteria

Requirement fields: Problem / User / Outcome / Scope / Open questions. Acceptance criteria use Given / When / Then.

For LUM-101, record Problem: the fictional joiner does not yet understand a task; User: a learner exploring onboarding; Outcome: the learner can inspect supporting guidance before deciding to complete the task; Scope: the four-step exercise flow; Open questions: which task explanations need clarification? Keep unresolved questions visible rather than filling gaps with invented policy.

Write stories as As a <role>, I want <action>, so that <outcome>. Example: As a learner, I want to inspect a task's published guide, so that I can understand the action before marking it complete. Use this story to draft behavior that can be observed through the learner interface.

Acceptance example AC-01: Given a learner is viewing a task with a published guide, When the learner opens that guide, Then the guide's supporting instructions are readable. Acceptance example AC-02: Given the learner understands the task, When the learner marks it complete, Then that learner's checklist progress includes the task. Neither reading nor asking a question completes a task automatically.

## Flow and traceability

Map the sample flow as choose role -> read task -> inspect published guide -> mark task complete. Label the learner decision between reading the guide and marking completion; the learner may leave a task incomplete. Describe the visible result at each step rather than an internal implementation.

Trace each criterion to LUM-101 and its scenario ID. The exercise traceability rows are LUM-101 -> learner story -> AC-01 -> guide reading check, and LUM-101 -> learner story -> AC-02 -> completion/progress check. Review that each criterion has a requirement, a scenario ID and an observable check. Flag any unsupported requirement or missing check as an open question.

## Refinement practice

Prepare a small unsent refinement note with Decision / Rationale / Remaining question. Example Decision: keep guide reading and task completion as separate learner actions. Rationale: reading provides context while completion is self-reported. Remaining question: which explanation should be clarified first? Include LUM-101 and the relevant AC-01 or AC-02 reference, then self-review the note against the brief, glossary, scope and traceability rows. This guide establishes no approved delivery budget or release commitment for LUM-101.
